## Requirements simplified, and why

- **Choosing featured products is a config change, not an admin screen.** An admin screen needs authentication and storage, which is a lot of work for a proof of concept. The service only asks "which IDs are featured?", so the source of that list can change later without touching anything else.
- **Enquiries are emailed, not stored.** If the email server is down, the customer sees an error (503) and can try again; nothing is lost silently. Storing first is the next step.
- **Smoke tests run locally, not in CI yet.** They need the running services and the live Fake Store API. Running them in CI is the next step (below).
- **No real visual design.** The creative work is happening separately. All colours, fonts and spacing are CSS variables in `apps/web/src/theme/tokens.css`, ready for the brand.
- **No infrastructure as code.** Not required. The containers and configuration are ready for AWS (see below).

## Smoke tests for the five main scenarios (added at my request)

The first test suite covered each layer well (unit, API and UI tests), but nothing ran the **real frontend against the real backend**: the web tests use a mock API, which could drift from the real one. I asked for smoke tests covering all five scenarios in the brief's acceptance criteria, run against the live system: the web app, the API, the live Fake Store data and the Mailpit inbox.

| Scenario (acceptance criterion)               | Smoke test in `e2e/catalogue.spec.ts`                                                                                                  | What it checks                                                                                                                                              |
| --------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. Home page shows the 5 chosen products      | "shows the 5 chosen top rated products, in order"                                                                                      | The page shows exactly the 5 products the API returns for `/api/products/featured`, in the same order                                                       |
| 2. Category page shows top rated + more       | "a category link shows top rated and additional products"                                                                              | Clicking "Electronics" in the nav opens `/categories/electronics`; both sections list exactly what the API returns                                          |
| 3. Search shows only matching products        | "clicking Search shows only products matching the term" and "a term with no matches shows the empty state"                             | Typing "jacket" and clicking Search shows exactly the API's results, and every result contains "jacket"; a nonsense term shows "No products match"          |
| 3b. Search as you type (added feature)        | "3+ characters show live suggestions; clicking one opens that product" and "the Search button searches for exactly what is in the box" | Two characters call nothing; at 3+ the dropdown lists the API's matches (max 5); clicking one opens that product; Search uses the box's current text        |
| 4. Product tile opens the details page        | "clicking a product tile opens its details page" and "an unknown product shows a not found message"                                    | The page heading matches the tile's title and the Enquire button is there; an unknown ID shows the not-found message                                        |
| 5. Enquiry emails sales and shows "Thank you" | "submitting the form emails the sales inbox and thanks the customer"                                                                   | Empty submit shows validation; a valid enquiry shows "Thank you"; **the email is found in Mailpit** with the right subject, recipient, reply-to and message |

How they're built:

- **Compare with the API, don't hard-code.** Product data is live, so each test asks the API what should appear and checks the browser shows exactly that.
- **The enquiry test checks the email really arrived,** using a unique token in the message to find it in Mailpit's API.
- **One worker,** because the tests share one inbox and the enquiry rate limit.
- **Not part of `npm test`,** because they need running services and network access. `npm run test:e2e` starts the services itself if they aren't already running, or targets the Docker stack with `E2E_BASE_URL=http://localhost:8080`.

## How the design supports growth beyond the PoC

| Expected change                                              | Where it happens                                                                        | What stays the same                                                                    |
| ------------------------------------------------------------ | --------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| New product data source (database, e-commerce platform, CMS) | A new class implementing `ProductRepository`, registered in `apps/api/src/container.ts` | Services, routes, the API contract and the web app                                     |
| New email provider (e.g. Amazon SES)                         | Point the SMTP settings at SES, or add an `EmailSender` adapter                         | `EnquiryService` and everything above it                                               |
| New look and feel                                            | `tokens.css` and component styles                                                       | Pages, data fetching and tests (tests find elements by role and text, not CSS classes) |
| More traffic                                                 | Swap the in-memory cache and rate limit for Redis; run more API containers              | The cache is a decorator around any repository                                         |
| Search that scales                                           | Implement `search()` in the new data source (SQL full-text, OpenSearch)                 | `search()` is already part of the repository interface                                 |

**AWS path:** API container on ECS Fargate or App Runner, web app on S3 + CloudFront (or the same nginx container), SES for email, Secrets Manager for settings, CloudWatch for the JSON logs.

## Implementation choices worth knowing

- **API contract shared through types:** `packages/shared` holds the `Product` type and the enquiry schema, used by both apps.
- **Validation twice, one schema:** the web app validates for instant feedback; the API validates because clients can't be trusted.
- **The server looks up the product for an enquiry**, so the email never contains a title or price sent by the client.
- **Fake Store quirk:** an unknown product ID returns HTTP 200 with an empty body. The adapter turns that into "not found" (404).
- **Errors:** one response shape for all errors (`{ error: { code, message } }`). Upstream failures are 502, email failures 503, and internal details are logged, never returned.
- **Security basics:** helmet headers, a 10 kb body limit, rate limits (120 a minute across the API, 5 enquiries a minute per IP), a honeypot field, HTML escaping and header-injection protection in the email, no personal data in logs, a strict CSP from nginx, and non-root containers. The API port isn't published, so the client IP header used for rate limiting can only come from nginx.
- **Caching:** an in-memory cache with a time limit and a size limit, sharing one upstream call between concurrent requests and never caching failures.
